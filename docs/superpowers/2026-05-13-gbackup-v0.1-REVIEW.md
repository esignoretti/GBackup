# GBackup v0.1: Code Review Report

**Reviewed:** 2026-05-13T19:30:00Z
**Depth:** deep (cross-file analysis with import graph tracing)
**Files Reviewed:** 32
**Status:** issues_found

## Summary

This review covers the full v0.1 implementation of GBackup — a Go CLI tool for backing up Google Workspace to S3-compatible storage. The implementation is structurally sound with clean separation between config, storage, metadata, and backup packages. Code compiles cleanly, `go vet` passes, and all tests pass under `-race`.

**However, 7 BLOCKER issues were found**, several of which produce incorrect behavior that would not be caught by existing tests. The most serious are:

1. **Drive backup backs up the same files for every user** — no user-scoped Drive query filter
2. **`--target-user` restore flag completely ignored** — always restores as admin
3. **`--date` restore flag has no effect on filtered items**
4. **Gzip errors silently discarded, causing silent data corruption**
5. **`Users.Include: "*"` doesn't list directory users** — just backs up the admin
6. **`resolveStatusUsers` returns exclude list instead of include list**

**Verdict: NOT merge-ready.** The core backup logic has correctness bugs that need fixes before this code ships.

## Critical Issues (Must Fix)

### CR-01: Drive backup backs up same files for every user (no user-scoped query)

**File:** `internal/backup/drive.go:100-111`
**Issue:** The `BackupUser(ctx, user, full)` method is called for each resolved user, but `Files.List()` has no query filter (`q` parameter) scoped to the user. The call uses `Corpora("allDrives")` which returns ALL files visible to the service account. Every user iteration downloads and uploads the identical file set, overwriting previous per-user S3 paths. Per-user tracking in SQLite metadata is therefore meaningless — ItemIDs will collide since the same file appears for every user. This also multiplies bandwidth/cost by the number of users.

**Fix:** Add a `q` parameter filtering by the user being backed up, or scope the Drive service per-user via impersonation. For example, set `Q(fmt.Sprintf("'%s' in owners", userEmail))` on the query, or recreate the Drive service impersonating each user:

```go
// Option A: Filter by owner
call := d.driveSvc.Files.List().
    Context(ctx).
    Corpora("allDrives").
    Q(fmt.Sprintf("'%s' in owners", user)).
    // ... rest of params

// Option B: Impersonate each user (requires per-user service)
svc, err := drive.NewService(ctx,
    option.WithCredentialsFile(d.cfg.ServiceAccountFile),
    option.WithScopes(drive.DriveReadonlyScope),
    option.ImpersonateCredentials(user), // impersonate the target user
)
```

Option A is simpler. Option B is more correct for per-user quotas.

### CR-02: `--target-user` flag has no effect on actual restore

**File:** `internal/restore/drive.go:28-44`
**Issue:** The `targetUser` variable is computed on lines 42-44 but never passed to the Drive API client. The Drive service is always created impersonating `r.AdminEmail` (line 31). The `--target-user` flag only changes the dry-run message text on line 48. For migration use cases (restoring to a different user), the flag silently does nothing — restored files always go to the admin's Drive.

**Fix:** Create the Drive service impersonating `targetUser` when `--target-user` is set:

```go
targetUser := r.TargetUser
if targetUser == "" {
    targetUser = r.User
}

svc, err := drive.NewService(ctx,
    option.WithCredentialsFile(r.ServiceAccountFile),
    option.WithScopes(drive.DriveScope),
    option.ImpersonateCredentials(targetUser), // Use targetUser here
)
```

### CR-03: `--date` flag has no effect on restore filtering

**File:** `internal/restore/drive.go:55-58`
**Issue:** The `--date` flag is parsed and used only to name the restore folder (`"GBackup Restore - 2026-05-13"`). The actual items to restore come from `r.MetaDB.ItemsByService("drive", r.User)` which returns ALL items ever backed up. If a user specifies `--date 2026-04-01`, they expect only items backed up before that date, but ALL items are restored regardless. This makes point-in-time recovery non-functional.

**Fix:** Filter items by the requested date before restoring:

```go
dateStr := r.Date
if dateStr == "" || dateStr == "latest" {
    dateStr = time.Now().Format("2006-01-02")
}
dateCutoff, err := time.Parse("2006-01-02", dateStr)
if err != nil {
    return fmt.Errorf("invalid date format: %w", err)
}

var filtered []*metadata.Item
for _, item := range items {
    if !item.ModifiedAt.After(dateCutoff.Add(24 * time.Hour)) {
        filtered = append(filtered, item)
    }
}
items = filtered
// ... proceed with filtered items
```

### CR-04: Gzip write errors silently discarded — silent data corruption

**File:** `internal/backup/drive.go:140-144`
**Issue:** Three error sources in the gzip compression pipeline are silently consumed:

1. `io.Copy(gw, content)` — if the download response is truncated, only partial data gets into the gzip buffer
2. `gw.Close()` — if the gzip footer can't be written, the compressed stream is corrupted
3. `content.Close()` — if the HTTP response body close fails, partial data may have been used

A corrupted gzip object is uploaded to S3 with no error. On restore, `gzip.NewReader` will fail, and the user gets a confusing "invalid gzip header" error instead of "download was interrupted."

**Fix:** Check all three error returns:

```go
var buf bytes.Buffer
gw := gzip.NewWriter(&buf)

_, err = io.Copy(gw, content)
content.Close() // close source regardless

if closeErr := gw.Close(); closeErr != nil {
    return count, fmt.Errorf("gzip close: %w", closeErr)
}
if err != nil {
    return count, fmt.Errorf("gzip copy: %w", err)
}
```

### CR-05: `Users.Include: "*"` backs up only the admin (not all directory users)

**File:** `internal/backup/runner.go:69-78` and `cmd/status.go:50-54`
**Issue:** When `cfg.Users.Include == "*"`, the spec says "back up all users." However, `resolveUsers` in runner.go returns `[]string{cfg.Workspace.AdminEmail}` — it only backs up the admin. The `DirectoryService.ListUsers()` method in `internal/gws/directory.go:34` exists and works but is never called. The same pattern is duplicated in `cmd/status.go:50` (`resolveStatusUsers`).

The Directory API integration (Task 7) was implemented but left disconnected. Any user expecting "*" to mean "all active users" will only have the admin backed up.

**Fix:** Connect the Directory API in `resolveUsers`:

```go
func (r *Runner) resolveUsers(ctx context.Context) []string {
    cfg := r.cfg.Config
    if cfg.Users.Include == "*" {
        dirSvc, err := gws.NewDirectoryService(r.cfg.DirAuth)
        if err != nil {
            return []string{cfg.Workspace.AdminEmail} // fallback
        }
        users, err := dirSvc.ListUsers(ctx)
        if err != nil {
            return []string{cfg.Workspace.AdminEmail}
        }
        var emails []string
        for _, u := range users {
            if !u.IsSuspended {
                emails = append(emails, u.PrimaryEmail)
            }
        }
        return emails
    }
    // ... existing logic for explicit user list
}
```

### CR-06: `resolveStatusUsers` returns exclude list instead of include list

**File:** `cmd/status.go:50-54`
**Issue:** When `cfg.Users.Include != "*"`, the function `resolveStatusUsers` returns `cfg.Users.Exclude` on line 54. This is logically inverted — it should return the included users, not the excluded ones. The `Exclude` field is a `[]string` while `Include` is a `string` (comma-separated), so the types don't even match directly corrective action needed.

This means `gbackup status` shows backup info for the wrong set of users.

**Fix:** 

```go
func resolveStatusUsers(cfg *config.Config) []string {
    if cfg.Users.Include == "*" {
        return []string{cfg.Workspace.AdminEmail}
    }
    // Split and trim the include list
    parts := strings.Split(cfg.Users.Include, ",")
    for i := range parts {
        parts[i] = strings.TrimSpace(parts[i])
    }
    return parts
}
```

### CR-07: `--dry-run` prompt not implemented per spec — restore runs immediately

**File:** `internal/restore/drive.go:47-52` and `cmd/restore.go:22-74`
**Issue:** The spec (line 161) states: *"Always runs `--dry-run` first with a confirmation prompt before actual restore."* Currently, `--dry-run` mode works correctly when the flag is set, but when not set, the restore proceeds immediately with no confirmation prompt. The user has no chance to preview what will be restored before actual writes occur Mend that.

**Fix:** In the restore command's `RunE`, always perform a dry-run preview first and prompt for confirmation:

```go
// In restore.go RunE:
r := &restore.DriveRestore{...}
r.DryRun = true // always preview first
if err := r.Run(context.Background()); err != nil {
    return err
}

fmt.Print("Proceed with restore? [y/N]: ")
var confirm string
fmt.Scanln(&confirm)
if confirm != "y" && confirm != "Y" {
    return fmt.Errorf("restore cancelled")
}
r.DryRun = restoreDryRun // restore original flag
r.Run(context.Background())
```

## Warnings (Should Fix)

### WR-01: `status` command uses `os.Getenv("HOME")` instead of `os.UserHomeDir()`

**File:** `cmd/status.go:22`
**Issue:** All other commands use `os.UserHomeDir()` which is cross-platform and respects OS conventions. `status.go` uses `os.Getenv("HOME")` which is Unix-only and returns empty string on Windows if HOME is unset.

**Fix:**
```go
home, _ := os.UserHomeDir()
dbPath := filepath.Join(home, ".gbackup", "meta.db")
```

### WR-02: `ModifiedTime` parse error silently dropped

**File:** `internal/backup/drive.go:122`
**Issue:** `modTime, _ := time.Parse(time.RFC3339, f.ModifiedTime)` silently discards the parse error. If Google returns a timestamp in a non-standard format, `modTime` will be the zero value (`0001-01-01 00:00:00 UTC`), which is stored in SQLite metadata.

**Fix:**
```go
modTime, err := time.Parse(time.RFC3339, f.ModifiedTime)
if err != nil {
    return count, fmt.Errorf("parsing modified time for %s: %w", f.Id, err)
}
```

---

### WR-03: Schedule and retention config parsed but never validated or applied

**File:** `internal/config/config.go:33-43`
**Issue:** `ScheduleConfig` (Incremental, Full cron expressions) and `RetentionConfig` (IncrementalDays, FullBackups, AutoPrune) are fully parseable from YAML but never validated or used by any code. The spec requires retention pruning after full backups. Users can configure retention values that silently have no effect.

**Fix:** Either implement retention pruning in the backup flow, or remove these fields from v0.1 config. If deferring to v0.2, add validation to reject non-zero retention values (fail early) or clearly document as unused.

### WR-04: Template execution error silently ignored in web dashboard

**File:** `web/server.go:43`
**Issue:** `tmpl.Execute(w, DashboardData{...})` returns an error that is never checked. If template execution fails (e.g., nil pointer dereference in template), the user gets a blank page or partial HTML with no error indication.

**Fix:**
```go
if err := tmpl.Execute(w, DashboardData{...}); err != nil {
    http.Error(w, "internal error", http.StatusInternalServerError)
}
```

### WR-05: Service account key path resolution is fragile

**Files:** `cmd/backup.go:49`, `cmd/restore.go:59`, `internal/backup/runner.go:50`
**Issue:** The service account file path is derived as `cfg.Workspace.AdminEmail + ".json"` — a relative path with no directory. The code never validates this file exists before attempting to create API clients. The error message users get ("unable to read credential file") is confusing because they don't know where the tool expects the file to be.

**Fix:** Add a config field for the service account key path, default to `~/.gbackup/service-account.json`, and validate it exists during `config.Load()` or command initialization.

### WR-06: No tests for cmd/, restore/, or web/ packages

**Files:** `cmd/*.go`, `internal/restore/drive.go`, `web/server.go`
**Issue:** These packages have zero tests. The restore logic (CR-02, CR-03 bugs), web dashboard error handling, and all CLI command wiring are untested. Critical bugs would only be discovered at runtime.

- Unit tests for `extractFileName` in restore package
- Unit tests for `resolveStatusUsers` in cmd package

### WR-07: S3 secret access key in plaintext on disk

**File:** `internal/config/config.go:114`
**Issue:** The config file saving uses `0600` permissions (good), but S3 credentials are stored as plaintext. Anyone with local access to the user's home directory can read them. While YAML config storage is spec'd behavior, this should be documented as a security consideration.

**Fix (future):** Consider supporting environment variable overrides (`GBACKUP_S3_ACCESS_KEY`, `GBACKUP_S3_SECRET_KEY`) with higher precedence than config file values.

**Fix:** See CR-02 fix. At minimum, document that `TargetUser` is not yet wired to API impersonation.

## Info Items

### IN-01: Redundant `~/.gbackup` path construction in 5+ commands

**Files:** `cmd/backup.go:35-38`, `cmd/meta.go:28-31`, `cmd/meta.go:82-84`, `cmd/restore.go:47`, `cmd/status.go:22`, `cmd/init.go:43`
**Issue:** Every command independently constructs the `~/.gbackup/` path using `os.UserHomeDir()` (or `os.Getenv("HOME")`). If this path changes (configurable data dir), every command must be updated.

**Fix:** Add a utility function in the config or a new `internal/paths` package:
```go
func DataDir() string {
    home, _ := os.UserHomeDir()
    return filepath.Join(home, ".gbackup")
}
func MetaDBPath() string {
    return filepath.Join(DataDir(), "meta.db")
}
```

## Recommendations

1. **Prioritize CR-01 first** — The duplicate-file-backup bug is the most impactful correctness issue; it makes per-user tracking meaningless and multiplies storage costs.

2. **Add integration test for Drive backup flow** — The current tests only exercise mime-type categorization and user filtering. A mock or integration test for `BackupUser` would have caught CR-01.

3. **Add restore command tests** — CR-02 and CR-03 would have been caught with even basic unit tests.

4. **Consider extracting path utilities** — The repeated `os.UserHomeDir() + "/.gbackup"` pattern across 5+ files is a maintenance liability (IN-01).

5. **Wire DirectoryService into resolveUsers** — v0.1 ships with a fully implemented directory listing feature that is completely disconnected from the backup flow (CR-05).
